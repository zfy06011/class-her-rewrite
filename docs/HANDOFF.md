## 3. 已确认的架构决策

### AD-1：单模块、严格分层、单向数据流

首版一个 Android 应用模块，按界面、业务规则、数据、平台适配分包。界面不能直接调用数据库或学校网页；业务规则负责周次、调课和合并；数据层统一写入；学校及文件适配器不自行修改课程。暂不按功能拆 Gradle 模块。

### AD-2：学校基线、本地修改、单次例外分开保存

保存学校基线、按字段的本地覆盖、单次例外和供页面读取的最终课表；同一事务更新相关业务数据。学校只改教师而本地只改教室时可自动合并；同字段双方变化不一致则待用户选择。单次例外以课程 UUID + 原上课日期关联，移动日期不改变身份。常规课程变化不自动撤销例外，而是提示关联变化。手工新增独立于学校来源。
### AD-3：稳定身份与保守匹配

每条上课安排拥有稳定 UUID，编辑与备份不改变它。可靠学校安排 ID 按学校、来源账号、学期限定作用域后关联本地 UUID；课程代码不能替代安排 ID。无可靠 ID 时先匹配完全一致记录；变更关联有歧义则人工确认。名称或可变字段哈希不得作为永久身份。未确认前保留本地课程及修改。

### AD-4：更新期间禁止编辑

从获取、解析、合并到提交，锁定正在更新的学期，仍可查看原课表；阻止该学期新增、编辑、删除、调课及重复导入，备份恢复不得并发执行。锁由公共写入入口执行，不能仅禁用按钮。

自动和手动检查共用同一更新任务；用户正在编辑时自动检查延后。成功、失败、超时、取消均解锁；登录失效结束任务并解锁。不得持有数据库事务等待网络。合并完成后短事务提交基线、修改、冲突与最终课表；待确认项落库即解锁，不等待用户处理。后续处理冲突时校验相关数据版本；进程退出后丢弃未提交结果，重启不遗留永久锁。

### AD-5：学校接入与通用规则隔离

学校适配器负责登录、会话、获取原始课表；解析器输出统一课程安排、来源身份、学期、完整性信息和解析疑点；业务层负责匹配、合并、保存。明确区分需登录、网络失败、解析失败、不完整结果和完整结果，不能把失败包装成空课程列表。首版只实现山东女子学院，无多学校界面或动态脚本平台。

### AD-6：节次与自定义时间互斥

每条安排选择节次集合或明确开始／结束时间。节次由学期作息表映射；非连续节次分段，不把第 1、2、5 节显示成第 1～5 节连续上课。修改作息表先预览影响，确认后重算；自定义时间不受影响。单次调课可单独选择模式。按 Asia/Shanghai 解释课程日期与时间，手机时区变化不改变安排；正在上课区间为开始包含、结束不包含。

### AD-7：统一学期与教学周语义

学期包含第一教学周的周一及总周数；输入其他星期需确认对应周一。周次保存明确整数集合，单双周和范围只作为输入方式。每条安排只有一个星期位置，同门课多个星期分别保存。常规日期按学期起点、教学周、星期计算，再应用例外。节假日不自动推断停课或补课。修改学期起点／周数先预览；已有例外保留原日期，失去关联或越界需处理后保存。

### AD-8：教务删除视为本地隐藏

用户删除教务课程时仅隐藏，保留来源、学校基线、本地修改与例外；再次导入不自动恢复，学校变化仍保持隐藏并提示。提供恢复隐藏课程入口，恢复前展示最新学校数据及保留修改。手工课程删除时移除课程与例外。隐藏标记进入备份。

### AD-9：学校删除需显式处理

仅完整有效快照中的缺失可生成删除候选；未确认期间保留本地课表，提示学校已移除。可确认删除课程及关联修改／例外，或将当前有效内容转为手工课程，保留 UUID 与例外。重复检查不重复生成同一待处理项。

转为手工课程后解除主动同步关联，但保留不驱动更新的历史来源映射，以识别学校后来重新出现的同一来源并询问重新关联；不能直接新增重复课程。

2026-10-06 用户确认：已隐藏学校安排转手工时保持隐藏、UUID、当前内容和单次调整；继续提供恢复入口，只有明确恢复后才显示。正常手工新增课程不参与学校删除判断。

### AD-10：登录失效不打断查看

自动检查发现会话失效，结束更新并解锁，仅显示登录提示；用户主动进入学校页面，成功后重新获取。学校会话与课程数据隔离，不写入业务数据库、备份或日志；可清除会话而保留课程。网络失败不立即循环重试，自动尝试应有退避，手动可重试。具体超时与退避参数由接入验证后确定。

### AD-11：带版本的完整备份快照

包含学期、作息、UUID、来源关联及历史映射、学校基线、本地修改、单次例外、隐藏标记、待处理冲突与设置；不含学校凭据／会话。导出读取一致快照。恢复先校验格式版本、数据范围和引用关系，展示时间、学期数、课程数，确认后整体替换；恢复期间禁止编辑与更新，失败保留原数据。

成功恢复后清除学校会话与自动检查计时，重新登录并核对来源身份后才允许自动更新。恢复不能留下半套课程与半套设置；跨 Room／DataStore 的代次切换原子恢复机制已于 2026-10-06 确认（第 21 节），实现与故障注入尚待验证；不能用两个连续写入冒充事务。

### AD-12：新应用升级显式迁移

首版即保存 Room schema；后续变更提供并测试迁移路径，保留 UUID、来源关联、手动修改、例外与冲突。不允许使用破坏性迁移回退，失败保留数据库并阻止继续写入、明确提示。数据库版本与备份格式版本独立；受支持的旧备份先转换再校验恢复。GitHub Actions 验证迁移与备份兼容性，小米 14 验证覆盖升级。此规则不要求迁移旧项目数据库。

## 4. 实现时必须闭合的共享契约

以下是上述决策的实现约束，不是额外产品功能；具体类名、表名由实现定义。

- 学校获取结果须附来源账号、学期与完整性；身份未知或与绑定不一致时不得合并已有课表。账号识别方式需在学校验证中查明，不假设可稳定取得。
- 字段合并比较旧学校基线、本地值和新学校值；两边改成相同值不算冲突。冲突记录保存比较依据和候选值，不能先覆盖依据后丢失冲突。新一轮学校变化要刷新／替代旧候选，不能让旧确认覆盖新数据。
- 单次例外、隐藏和手工来源不被自动合并清除；被首次导入明确排除的条目保留排除信息，避免当次结果被误标为完整无疑点。
- 写入统一经过协调入口：编辑、更新、确认冲突、学期调整、备份恢复均遵守互斥规则。提交同时更新原始业务数据和最终课表；最终课表是可重建投影，不是第二份可独立编辑的数据。
- 导出 JSON 是业务快照，不直接复制正在使用的数据库文件；备份导出失败不得报告成功。恢复需要验证数据与设置共同生效以及崩溃恢复。

## 12. 2026-10-02 电脑端执行结果：登录后直接读取

### 12.1 当前结论

**电脑端学校数据获取路径通过；用户不需要导出或选择课表文件。** 用户已在 Codex 内置电脑浏览器亲自登录并回复“已登录”。agent 打开“教学安排 → 个人课表”，确认选中 2026-2027 学年第一学期（`2026-0`）。登录主页面及课表框架实际使用 HTTPS，未绕过浏览器安全提示或验证码。

发现并在现有登录会话内成功请求学校个人课表显示接口：`GET https://jwxt.sdwu.edu.cn/sdnzjw/student/wsxk.xskcb10319.jsp`。请求带 `params`；实测它是学校页面对 `xn`（学年）、`xq`（学期）、`xh`（当前账号学号）参数串的 Base64 封装。具体参数值和完整请求 URL 不写入文档。Base64 不承担加密或认证，会话仍由学校正常登录维护；不得通过变更 `xh` 查询其他用户。

agent 读取当前个人课表表单中的账号、学年和学期，在浏览器会话内动态构造请求，使用 `fetch(..., {credentials: 'same-origin'})` 重取；HTTP 200，`text/html;charset=GBK`，三张表。返回账号与当前表单一致，星期网格内容与用户看到的个人课表逐字归一化比较一致。此过程未调用导出按钮、未调用 Excel 导出接口、未生成新下载文件，数据只在浏览器内存中处理。

因此首选实现流程维持已确认架构：**用户首次在学校页面登录 → 学校适配器使用会话直接获取 HTML → Kotlin 解析为统一模型 → 预览／合并 → 本地事务保存**。第 10 节“改成用户导出文件”的说法属于历史建议，不作为当前首版方案；无需减少“超过 6 小时自动检查”的硬要求。

## 21. 备份恢复原子设计（2026-10-06 已确认，未实施）

这是 AD-11 和第 5 节原子恢复缺口的具体方案。用户选择“采用代次切换方案（推荐）”，已批准该机制及下面的中断规则；目前只完成设计记录，没有改设置、恢复代码或数据库结构。后续完整备份实现还须覆盖尚未完成的来源历史映射和待处理冲突，不能只备份当前界面投影。

### 当前事实与边界

- 当前 PreferenceSettings 使用一个 theme key，并把 IOException 变为空设置；ViewModel 分别收集 settings.theme 和 repository.observeSchedules，两个回调各自更新 state。直接连写 Room 和此 DataStore 无法满足课程／设置共同生效与失败原数据保留。
- [DataStore 官方 API](https://developer.android.com/reference/androidx/datastore/core/DataStore) 明确 updateData 的写入成功返回以持久化完成为界，并在 transform／写盘失败时中止；[Room Transaction API](https://developer.android.com/reference/androidx/room/Transaction) 以事务成功／异常决定提交或回滚。这些是各自的事务，**不证明二者天然共享事务**。
- 继续 Room 保存业务、DataStore 保存轻量设置；不切换栈，不复制运行中的 DB 文件，不导出学校凭据／会话。跨存储原子性通过准备设置代次和 Room 激活指针获得，仍须实现与故障注入验证。

### 已确认机制

1. Room 增加当前激活设置代次 metadata（稳定初始 legacy 代次），课程业务数据和该指针在同一 DB 事务中提交。DataStore 保留按代次的不可变设置快照；普通设置修改更新当前激活代次。迁移期只有 legacy 代次可读旧 theme key，其他代次缺失不能默默用默认主题顶替。
2. 校验带独立格式版本的业务 JSON：学期／作息、UUID、关系、基线、手工内容、本地覆盖、单次例外、隐藏、历史映射、待处理冲突和设置。展示恢复摘要，用户确认后才进入公共全局写入锁；主题修改也必须接此锁，避免恢复期间独立设置写入。
3. 在不改当前激活设置的前提下，用 DataStore.updateData 写入新代次 g1，等待持久化成功；失败／取消时 DB 不动，旧数据和旧设置继续生效。新分支暂时不可见，不以准备成功宣称恢复成功。
4. Room 短事务整体替换已校验业务内容、清除成功检查计时、设置重新登录 gate，并将激活指针切到 g1。网络与文件读取／DataStore 写入均不放入此 DB 事务；DB 失败／取消整体回滚，仍读旧代次 g0，g1 只是可稍后清理的未激活分支。
5. **提交点是上述 Room 事务提交**。提交前取消保留旧状态；提交后不能再把清理失败或晚到的取消报告成“恢复失败、原数据未变”。以持久化的激活代次判断是否已生效；必要的短提交／结果识别保持不可被中断成错误报告，不扩大为不可取消的全程。
6. UI 不再以两个独立 flow 回调更新课程／设置；统一应用快照读取 Room 业务＋激活代次，并订阅该代次的 DataStore 设置，完整成对后一次更新 state。准备 g1 不发新外观；Room 激活 g1 时必须同时交付新课程＋g1 设置。所选代次缺失／设置损坏时明确报错并阻止写入，不显示半套数据，不默默清空或设默认。
7. 恢复提交后启动学校会话清理；Room 的重新登录 gate 必须先持久化，自动检查在会话清理／重新登录／来源核对完成前不能启动。进程在清理前退出时，重启先补清理，不能复用旧学校会话。未激活旧／新设置分支的清理只在可确认激活指针后进行，不影响恢复成功与当前数据。

### 中断／失败语义与必须验证项

- 读文件、校验、摘要确认之前：不改任何当前业务／设置。
- DataStore 新代次准备失败，或准备后 DB 尚未开始／DB 中断：g0 业务＋g0 设置，不能出现 g0＋g1。
- Room 提交完成后进程终止：重启读 g1 业务＋g1 设置；先完成会话清理和登录 gate，不能出现 g1＋g0。
- 当前代次设置损坏／缺失：报错并保护存储，不伪造成功；恢复成功后的孤立分支清理失败不回滚当前数据或冒充恢复失败。
- 必须有实际 DataStore 和 Room 磁盘故障注入、每个提交边界重开、观察者发射序列校验、取消前后结果识别、旧配置迁移、备份往返／坏文件／未知版本／引用错误及范围检查。设计推演不能替代这些测试，不能据此称原子恢复已验证。

### 确认结果

用户已明确采用 Room 激活指针＋按代次 DataStore 设置＋统一应用快照，允许新增 DB metadata 的显式迁移及调整 settings 读写与界面组合；继续原 Kotlin／Room／DataStore／Hilt 栈。架构授权来自本轮独立问题答复，不是把 0.2.3 推送授权扩展为架构授权。具体实现和故障注入仍未执行，不能称原子恢复已验证。
